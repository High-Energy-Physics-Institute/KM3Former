# Results

## detector_overlap_analysis_summary

Follow-up analysis in `runs/detector_overlap_analysis` indicates that the main bottleneck is detector-response overlap rather than a purely architectural failure: true class `1` events behave like a continuum between lower-activity class `0` events and higher-activity class `2` events when viewed through detector-observable features such as `active_hits` and `total_tot`. Detector-only cheap baselines reached about `0.484` to `0.485` test accuracy with class-`1` recall only `0.243` to `0.286`, while KM3Former improved to about `0.532` to `0.539` accuracy but still kept class `1` as the limiting factor.

The ambiguity diagnostics strengthen that conclusion: for both `exp_008_capacity_push` and `exp_009_capacity_push_retuned`, the model was least confident when it predicted class `1` correctly and more confident when true class `1` events were pushed toward class `0` or class `2`. Important caveat: the MC-truth energy comparison in `runs/detector_overlap_analysis` was used only as a diagnostic sanity check and is not available at real inference time; the operational verdict should therefore be based on detector-only baselines plus KM3Former, not on MC-augmented numbers.

## exp_001_baseline_local_smoke

Commit `4cec1d0`; used `data/muon_data_7224_7247.h5` with 21,555 events split into 17,244 train / 2,155 val / 2,156 test, and kept the baseline smoke setup in `runs/muon_count_smoke` (`model_dim=128`, `num_heads=4`, `num_encoder_layers=4`, `dim_feedforward=256`, `pairwise_neighbors=16`, `batch_size=32`, `epochs=1`, CPU). Best validation loss was `0.986383` and test accuracy was `0.502319`; confusion matrix (true rows, predicted cols) was `[[439, 140, 126], [309, 157, 233], [138, 127, 487]]`, so this is a usable baseline to keep. Initial note: the model already learned nontrivial structure after one epoch, but class `1` was the main weakness and was frequently confused with classes `0` and `2`.

## exp_008_capacity_push

Commit `52f65ff`; used the saved run in `runs/exp_008_capacity_push` with the resolved config from that directory (`model_dim=192`, `num_heads=8`, `num_encoder_layers=4`, `dim_feedforward=384`, `pairwise_neighbors=16`, `pooling=attention_mean_sum_count_concat`, `position_encoding=none`, `pairwise_time_transform=raw`, `pairwise_distance_transform=raw`, `batch_size=32`, `learning_rate=8e-4`, `epochs=10`). TensorBoard showed steady optimization through the full run: train loss improved from `1.342517` to `0.903591`, train accuracy from `0.418823` to `0.554996`, and validation loss from `1.006641` to a best of `0.939720` at epoch `9`. Validation accuracy improved from `0.470070` to a best of `0.538747` at epoch `9`, then stayed essentially flat at epoch `10` (`0.538283`), so this run looks like a real but modest gain rather than a broken training job.

The saved metrics confirm that the main weakness is still class `1`. Validation macro-F1 reached `0.527376`, but class-`1` recall was only `0.313305` and class-`1` F1 was `0.360494`; on test those dropped to `0.290415` recall and `0.339181` F1. Test accuracy finished at `0.532468` with macro-F1 `0.518452`, and the confusion matrices show that true class `1` is still most often pushed toward class `0`, with a secondary spillover into class `2`. Promotion note: keep this run as a stronger capacity reference, but do not treat it as the new best ablation yet because the middle-class confusion remains the limiting factor.

## exp_009_capacity_push_retuned

Commit `52f65ff`; used the saved run in `runs/exp_009_capacity_push_retuned` with the retuned follow-up config (`model_dim=192`, `num_heads=8`, `num_encoder_layers=4`, `dim_feedforward=384`, `pairwise_neighbors=16`, `pooling=attention_mean_sum_count_concat`, `position_encoding=none`, `pairwise_time_transform=signed_log1p`, `pairwise_distance_transform=log1p`, `batch_size=32`, `learning_rate=8e-4`, `epochs=15`). This run trained smoothly but did not improve the validation frontier set by `exp_008`: TensorBoard showed train loss improving from `1.413320` to `0.917246` and train accuracy from `0.409356` to `0.541255`, while validation loss reached a best of `0.950000` at epoch `11` and validation accuracy reached a best observed value of `0.534107` at epoch `14`. That makes the retuned run slightly worse than `exp_008` on both best validation loss and best validation accuracy.

The saved best-loss checkpoint confirms that restoring the pairwise transforms in this multiclass setup did not solve the middle-class problem. Validation accuracy at the saved checkpoint was `0.521578` with macro-F1 `0.503504`, and class-`1` recall fell to `0.258941` from `0.313305` in `exp_008`. Test metrics were mixed rather than clearly bad: accuracy nudged up to `0.538961` and macro-F1 to `0.519590`, but class-`1` recall still slipped to `0.271817`, and the prediction histogram became even less willing to emit class `1` (`429` predictions for class `1` on test versus `498` in `exp_008`). Promotion note: keep `exp_009` as a useful negative result showing that the restored `signed_log1p` / `log1p` transforms did not help this branch enough to justify promotion over `exp_008`.
